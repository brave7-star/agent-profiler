# Agent Profiler v0.1.0-dev

一个只读的个人编码 agent 环境体检工具，面向 macOS 上的 Claude Code 和 Codex。

它回答一个问题——**「我这套 agent 环境到底怎么样？」**——沿着一条每一环都要单独挣来的链：

```
Installed → Loaded → Used → Useful → Cost → Recommendation
```

这几个名字保留英文，因为它们同时是输出里的字段名（`installed` / `loaded` / `used` /
`useful` / `cost`）——分别是「装了」、「载入」、「用过」、「有用」、「成本」，最后是「建议」。

产物不是分数，而是证据链本身，以及一条规矩：**结论的强度不许超过证据的强度**。在真实环境
上，多数环节的结果是「未证明」，报告第一屏就会这么说。那是正确的输出，不是失败。

它建立在七条原则之上，中英文都在 `docs/principles.md` 里。

## 它拒绝说的话

读任何输出之前值得先知道，因为这是它和一块仪表盘的区别：

- **没有真实 A/B 就不给删除建议。**「去掉 X 能省 Y%」是禁止的，测试会在整个输出里 grep
  这种说法。
- **成本不等于浪费。** 一个组件可以每次请求都很贵、同时又被大量使用。两个事实都报，谁也不
  蕴含谁。
- **结论只允许说「留着」。** 有分离能证明影响；**没有**分离则归因不了，三个无法区分的原因
  摆在那里——组件不起作用、这个任务本来不需要它、或者基线本来就够好。「留着」是弃权，不
  需要证据；「删掉」是主张，而它的证据通常并不存在。
- **失败的测量按失败来报**，绝不省略，这样它就不会被误读成「从没测过」。
- **环节之间从不插值。** 装了不是载入的证据，用过不是有用的证据。

## 只读，这是一条承诺

被测对象就是使用者的真实配置，所以这个工具从不写它。`~/.claude`、`~/.codex`、`~/.agents`
底下的任何东西，以及 `CLAUDE.md`、`AGENTS.md`、`settings.json`、`config.toml`、`.mcp.json`，
都不会被修改、移动或创建。是工具去适应真实环境，不是反过来。

`--exclude NAME` 让某个 MCP server 完全不被连接。它依然会被清点、依然会被报出来——标注为
「按要求排除」，这样空白的成本格子就归因于使用者自己的决定，而不是工具的缺口。

## 范围：一个项目，还是整个环境

```bash
./bin/agent-profiler report --root ~/Projects/my-project          # 只看这个目录
./bin/agent-profiler report --root ~/Projects/my-project --all    # 看整个环境
```

会话记录是按工作目录归档的，所以只看一个项目会漏掉在别处做的活——包括声明在家目录那个项目
键下面的 MCP server，以及一个按日期而不是按路径存会话的宿主程序。`--all` 才是上面那个问题
真正需要的范围。

这个工具还会**认出自己的探针会话**。测量一套配置就得真的把宿主程序跑起来，而宿主程序会像
记录任何会话一样记录这些运行。不认出来的话，工具就会把自己的尾气算成使用者的工作、把自己
的开销记到被体检的人头上。这些会话有指纹，会从每一个面向使用者的总数里排除。

## 再跑一次

每个要遍历语料的阶段，都按文件的**内容哈希**做单文件缓存，绝不按大小加修改时间。一秒之内
的等长编辑对「大小 + 修改时间」是隐形的，而一个对改过的文件给出过期答案的体检工具，比一个
慢的更糟。缓存键还包含工具自身源码的指纹，所以改了解析器，它产出的一切都会失效。

`--no-cache` 全部重读，给不信任复用数字的读者。

**故意不缓存**的是任何归因到已安装组件的东西。一个已经知道装了哪些 skill 的缓存答案，会让
「装一个 skill 没改变结果」成立——那是一种长得像测量结果的陈旧。

## 最大的已知风险：n = 1

这里关于**宿主程序如何记录**的每一条结论，都是从一台机器的语料归纳出来的。这比任何覆盖缺口
都是更大的未知，而且再多分析也修不了它——它需要别的机器。

所以这些假设是**可执行的**：

```bash
git clone <this repo>
./bin/agent-profiler verify      # 只读，不发送任何东西，几秒钟
```

九条假设，三种结果：`hold`（成立）、`violated`（被推翻，并点出推翻它的那条记录）、以及
`no_evidence`——它**不是通过**，而是「这份语料里没有实例，所以这台机器对此说不了话」。一个
全新安装没有 rollout、也没有 MCP 调用，把那报成「一切正常」正是这个工具存在的目的所要避免
的过度断言。只被一两个实例确认的假设同样读作 `no_evidence`：一条格式不变量需要若干次确认，
一台机器才算对它有发言权。

写这个校验器的过程中发现了它自己的四个 bug，每一个都偏向「给第二台机器一个虚假的全部通过」。

### 第二台机器的价值

已经有一台跑过了。没有任何假设被推翻，而它测不了的那几条，恰恰是它的语料里没有实例的那几条
——这是机制在正常工作，不是缺口。

有价值的部分不是那张表，而是操作者手写补上的一句话：他们的 rollout 存储形式和这台机器不同。
这读起来像一个跨机器差异。其实不是——存储形式跟的是文件**年龄**，经由一个维护过程——但去核
实它的过程中，挖出了一个跟存储毫无关系、但大得多的缺陷。

宿主程序把 token 用量写在两种不同的记录里，出现哪一种取决于它的**版本**。采集器只读了其中
一个窄版本窗口里的那种记录，并且正确地拒绝对另一种求和（因为那个是会话累计值）——结果它对
绝大多数会话报告了**零 token**，而那份语料比它实际统计的大好几倍。一道防重复计数的护栏变成
了盲区，而输出里没有任何地方提到这件事。现在两种记录都读，分开存放在不同字段里（因为它们不
是同一个量），并给出一个覆盖率数字，说明有多少会话具备哪一类证据。

接着为那种记录写第九条假设，结果它**在写它的那台机器上**就报了 `violated`——这是正确的，因
为假设写得太宽了：宿主程序把同一种事件类型复用在限流通知上。把它收窄的同时，也修掉了那个刚
写一天的解析器里的一个新 bug：这样一条通知如果最后到达，会把一个真实的会话总量覆盖成零。

这些东西一样都不在第二台机器的命令输出里。它们来自一行散文——这就是为什么要去问一个人，而
不只是跑一条命令。

## 从一个速率到一个关于这套环境的数字

测出来的「每次请求 N 个 token」是一个速率，不是关于任何人环境的数字。把它变成那种数字所需
的请求量就在语料里，而且读它不花钱：一次模型回复就是一次请求。所以报告会做乘法，并且说清楚
它乘了什么。

三条规矩保证这件事诚实。请求数**排除工具自己的探针会话**。一个速率**只乘它自己那个宿主程序
的流量**，所以一个装在比测量范围更多的宿主程序下的组件，会被标上 `≥` 并点出被排除的那个宿
主程序。而这些行**从不相加**：一个 skill 装在两个作用域下会出现两次、却只带一份前缀，相加
就是把它算了两遍。

金额是被扣住的，而且卡点被精确点出：缺一个每 token 的价格，而它取决于模型、以及每次请求的
缓存状态。一个常驻前缀位于 prompt 的最前面，也就是最可缓存的位置，所以按完整输入价计费会严
重高估它。这个工具不替读者挑一个价。

## 未证明，以及它能不能改变

「未证明」读起来像还没干完的活，而对多数组件来说这是错误的读法：这个工具能跑的任何东西都改
变不了它们。所以每一条都被免费归类——只依据磁盘上已有的东西——分成「还只是缺一次测量」和
「这里的任何方法都测不了」，并点出原因：组件没有声明任何机器可判定的规则；一个 server 是在
配置里声明的、根本不带可引用的文字；一个文件是空的。这几种都不是花钱能回答的，而说清这一点
正是要点。

用来做这个判断的规则库，就是合规探针自己那一套。我先试过为分类器另写一组模式，结果它把一句
关于**工具返回值**的话、以及一个示例命令里的参数，当成了关于 agent 输出的规则——那会把付费
探针押在两个什么都没声明的组件上。

当一个组件可测、但装了内容互不相同的多份拷贝时，**每一份都测**，而不是测其中一份。宿主程序
只列出这个名字一次，也不记录它载入的是哪一份，所以单独一次测量会变成一个关于「某个说不清是
哪份拷贝」的结论。全测过之后，几份一致时结论就与拷贝无关，不一致时就把分歧点出来。

### 合规探针覆盖什么

一个指令文件和一个 skill 用同样的方式测量，因为一条机器可判定的规则不在乎是哪类组件声明了
它。只有实验臂不同：

| 组件 | 两个臂的差别 |
| --- | --- |
| 指令文件 | 追加一份逐字拷贝，或让它出现在工作目录里 |
| skill | 通过 `--plugin-dir` 加入一个 skill，来自真实目录的一份拷贝 |

skill 臂会把使用者自己的指令文件从**两个臂里都**清掉，所以那些文件同样声明过的规则，不可能
解释两臂之间的差异——是这条路线本身消除了这个混淆因素，而不需要事后辩解。它也绝不以 bare 模
式运行：bare 模式会跳过插件同步，那样这个参数什么都不会载入，而两个臂看起来却像有差别。

一个 skill 自带的 fixture skill 不是组件。有一个真实的 skill 把它们放在
`evals/fixtures/skills/<name>/` 下面，这满足「已安装」的每一条结构判据，所以嵌套是靠查找外
层的 `SKILL.md` 来识别的。去测它们等于凭空造出几个没人载入的安装。

`--plugin-dir` 是 Claude Code 的参数，所以 Codex 那侧的 skill 在这里没有实验臂，于是**不测**，
而不是用一条替代路线去测。

花钱之前有两道闸，都是从一次什么有用结果都没产出的运行里学到的：

- **实验臂必须真的带上那个组件。** skill 是靠描述匹配载入的，所以一个和它描述无关的任务永远
  到不了它，两个臂于是毫无差别。那读起来像「这个 skill 什么都没改变」，实际意思是「这个任务
  没碰到它」。现在会先让宿主程序列出自己有哪些 skill，而一个在本该带上它的臂里却不存在的
  skill，在任何东西运行之前就被拒掉。我先试过算「描述和任务的词重叠」，然后放弃了：用另一种
  语言写的描述几乎抽不出词，而某个真实描述里三个零碎的英文片段，跟一个关于分页 loop 的任务
  共享了 `loop`，于是它靠巧合通过了。
- **宿主程序不再回答时，整批中止。** 重试预算是按独立失败率设计的，所以面对一个持续性的状况，
  每一次尝试都会失败，而整批会一路花到撞墙为止——在促成这项改动的那次运行里是 90 次探针中的
  54 次。连续六次失败就放弃这一批，并且产物会说明它被放弃了，这样一份短记录就不会被误认成一
  份完整的。

失败会保留宿主程序自己的 stderr，而 `harness_health` 在顶部一次性报出每条臂的探针成功率。没
有这两样，一条死掉的臂和一堆普通的「未证明」就无法区分：在那次运行里，Claude 侧的每一个探针
都死了，而 Codex 侧的每一个都成功，输出里却没有任何地方说这件事。

## 要花钱的测量，以及它们前面那道闸

三个 `measure-*` 命令和 `evaluate --measure` 会真的运行宿主程序、花真钱。它们是「刻意花钱」
这条路，而且会在运行前说明这一点。

`judge` 和 `evaluate` 后面有一道「预期信息增益」闸：花钱之前，各自声明预期能学到什么、这个答
案值多少，当开销超过价值时就拒绝这笔交易。语义判官自己的第一次运行就没过这道闸——它花掉的比
它识别出的可避免浪费还多——现在是这道闸拒绝它，而不是仓库里只写一段教训。

探针可靠性是**被框定的，不是被解释的**：失败率被测出来，每条臂的重试预算由它推导，失败的花费
也被计入成本。原因未知，而这个结论被记录为「需要换一种方法」，不是记录成一个已解决的问题。

### 测量结果会自动留存

测量是这里唯一花钱的一步，也是唯一没法免费重新推出来的东西。所以 `measure-*` 和
`evaluate --measure` 在打到标准输出的同时，也会把结果写进
`~/.local/state/agent-profiler/measurements/`，而 `report` 和 `score` 会自动去读那个目录：

```bash
./bin/agent-profiler measure-instructions --root PATH --all   # 花钱，只花这一次
./bin/agent-profiler report --root PATH --all                 # 免费，而且带成本列
```

在这之前，测量结果只会打到标准输出。要喂回去，就得记住加 `--output`、记住文件存到了哪、而且
以后每次都要带 `--evaluation` —— 不带这个参数跑出来的报告**根本没有成本列**：整个项目里最贵的
那部分产出，默认看不见。想要一份带成本的报告，得先把好几份产物手工合并成一个文件。

这个存储是只追加的，一次运行一个纯 JSON 文件，位置可以用 `AGENT_PROFILER_STORE` 覆盖。
同一个文件的两次测量会**都留着**：两个读数不一致本身就是这个工具要报的一个发现，不是靠「谁更新
听谁的」来摆平的冲突。用留存数字生成的报告会在第一屏说明这一点，所以一个记下来的数永远不会被
当成刚测出来的数。

### 想用别的产物覆盖它

```bash
./bin/agent-profiler report --root PATH --all --evaluation EVAL.json --useful USEFUL.json
```

`--evaluation` 优先于留存的测量 —— 要拿一次新测量和留存的那份对比时，需要的正是这个。
两个产物都存在时就两个参数都传：只传一个，曾经静默丢掉了另一个的测量结果。

一次测量是按绝对路径或 server 名字关联到组件的，所以在另一台机器上产出的产物能解析、却关联
不到任何东西——而它本该证明的那些环节于是读作**从没测过**，这正是这个工具要防止的那一种混淆。
`report` 和 `score` 都带 `unmatched_measurements`，报告第一屏就会说有多少份传入的测量什么都没
匹配上、以及为什么。一个存在但落在扫描范围外的路径，会和一个根本不在这台机器上的路径区分开，
因为这两种需要不同的动作。

测量产物**不进仓库**。它们是一台私人机器的画像——家目录绝对路径、按名字列出的已安装组件、以及
在哪些目录下干了多少活。公开一个工具，不要求公开任何人的环境。在你自己的机器上跑这些命令，你
就得到你自己的。

## 命令

```
./bin/agent-profiler inspect   --root PATH [--all] [--exclude NAME] [--exclude-file FILE]
./bin/agent-profiler sessions  --root PATH [--all]
./bin/agent-profiler collect   (--root PATH | --session FILE) [--all] [--limit N]
./bin/agent-profiler normalize (--root PATH | --session FILE) [--all] [--harness H] [--events-out FILE]
./bin/agent-profiler analyze   (--root PATH | --session FILE) [--all] [--full]
./bin/agent-profiler report    --root PATH [--all] [--evaluation FILE] [--useful FILE] [--format text|json]
./bin/agent-profiler score     --root PATH [--all] [--profile P] [--preferences FILE] [--evaluation FILE] [--useful FILE]
./bin/agent-profiler verify    [--limit N] [--format text|json]
./bin/agent-profiler judge     --root PATH [--tier T] [--dry-run] [--force]
./bin/agent-profiler evaluate  --root PATH [--measure]
./bin/agent-profiler measure-instructions --root PATH [--pairs N]
./bin/agent-profiler measure-skills       --root PATH [--only NAME] [--pairs N]
./bin/agent-profiler measure-useful       --root PATH [--repeats N]
./bin/agent-profiler trace     --input FILE
./bin/agent-profiler compare   BASELINE.json CANDIDATE.json
```

每个子命令都接受 `--lang en|zh`、`--no-cache` 和 `--output FILE`。不给 `--lang` 时，语言依次
从 `AGENT_PROFILER_LANG`、`LC_ALL`/`LC_MESSAGES`/`LANG` 读取，最后回落到英文。

`trace` 是针对任意 JSONL 文件的、不认格式的兜底路径；`collect` 是认格式的那条路。

## 偏好，以及为什么分数通常被扣住

一个「考虑偏好」的分数需要某个人的偏好。没人提供的时候，这些 profile 是**这个工具自己命名的
假设**，而每份报告都会在一个机器可读的字段里这么说。

它们的用途是敏感性分析，不是排名：拿同一份证据在几套都说得通的偏好下各跑一遍，看答案会不会
变。一个排名在不同 profile 之间翻转的组件，正是证据无法决定的那个，而诚实的输出就是这个翻转
本身。

真实权重放在项目根目录的 `agent-profiler-preferences.json`，或者用 `--preferences` 指定。
参见 `docs/preferences.example.json`。

任何组件缺 `used`、`useful` 或 `cost`，整套环境的总分就被扣住。拿「恰好测到了哪几环」来排名，
会把证据最充分的组件排到最差——而这正是这个阶段存在要避免的那个具体失败。

## 安装

没什么要安装的。纯标准库，Python 3.9 或更新，`bin/agent-profiler` 是一个三行的壳。

```bash
PYTHONPATH=src python3 -B -m agent_profiler.cli verify     # 和那个壳等价
```

跑测试要用 `python3 -B`。不加 `-B` 时，一个按源文件大小和整秒修改时间来校验的字节码缓存，会
在一秒之内的等长编辑之后喂给你一个过期模块——而在某些安装里那个缓存还位于目录树之外，于是连
一个 `__pycache__` 都看不到。这个坑在这里真的耗掉了调试时间：`inspect.getsource` 显示的是一
回事，实际跑的字节码是另一回事。

```bash
for f in tests/test_*.py; do PYTHONPATH=src python3 -B "$f"; done
```

484 个回归测试，每一个都钉在一个真实运行里观察到的缺陷或格式性质上，而不是钉在某个假想情况上。
没有任何测试花掉一个 token。

## 格式笔记

`docs/dogfood/trace-schema.md` 和 `docs/dogfood/codex-schema.md` 记录两个宿主程序实际写下的
东西——记录类型、用量数据在哪里、哪些字段是累计值。这些是宿主程序的性质，也正是别的机器能够
推翻的那部分，所以中英文都有。

它们**故意不写**的是：背后那份语料有多大、引用的是哪些会话。一个体量描述的是机器而不是格式，
而一个会话 id 对打不开那个文件的读者什么都证明不了。读者需要的是「某条性质有没有反例」，而
`verify` 会拿你自己的语料重新核。同一条规矩也管源码：注释可以说测了什么、为什么重要，但不能把
某一台私人机器上各组件的尺寸抄进去。`tests/test_privacy.py` 按模式类别来守这条线——在那之前有
两轮扫描是一次性脚本写的，每一轮都只找到了作者当时记得去找的东西。
